# CLAUDE.md

This file is the project-memory contract for **Claude Code** working in this repository.
Claude Code reads `CLAUDE.md` at the project root on startup and treats its instructions
as always-applied. The goal of this file is to make Claude Code behave the same way the
Cursor agent already behaves in this repo (driven by `.cursor/rules/*.mdc`, `AGENTS.md`,
and the workspace skills).

**Project**: EPR Reporting Tool (Python report server, Jira sync, HTML reports, Azure App Service).
**Repo root**: `E:\JIRA SCRIPT` (Windows / PowerShell).
**Live site**: `https://epreporting.azurewebsites.net/` (App Service: `epreporting`, deploy workflow `.github/workflows/azure-appservice-deploy.yml`).

## 2. Report serving model (canonical sources + sync)

- Canonical report sources live in the **repo root** (for example `introduction.html`,
  `dashboard.html`, `approved_vs_planned_hours_report.html`) and are promoted into
  `report_html/` by `sync_report_html()` in `report_server.py`.

  `shared-nav.js`, `shared-nav.css`, `shared-date-filter.js`, and
  `report_html/material-symbols.css`.
- If a report output path changes or a new report is added, update
  `_resolve_report_html_sources()` in `report_server.py` so localhost serves the right
  file after sync.

## 3. HTML changes require coupled updates

Whenever you change any HTML in this repo, treat the change as **incomplete** until the
full serving chain is aligned:

1. **Find the canonical source first.** It may be a root-level `.html`, a template such
   as `dashboard_template.html` or `ipp_meeting_dashboard_template.html`, inline HTML
   inside Python, or output generated by a script.
2. **Update every dependent layer** that the markup relies on:
   - JavaScript selectors, handlers, and shared assets (`shared-nav.js`,
     `shared-date-filter.js`, etc.).
   - CSS selectors in root assets or the generated/template file.
   - Python generators or server code that emit, wrap, sync, or route that HTML.
   - Tests that assert on DOM, generated output, or served routes.
   - Relevant documentation when visible behavior or the verification path changes.
3. **Do not patch only a published copy under `report_html/`** when the canonical source
   lives elsewhere. Update the source file that `sync_report_html()` or the generator
   pipeline uses.
4. If a new report is added or a source path changes, update
   `_resolve_report_html_sources()` in `report_server.py`.

### Localhost readiness after HTML / generator changes

- If the change affects a generated report, rerun the narrowest generator or rebuild
  command so the source artifact is current before relying on localhost.
- If the change affects shared assets, edit the **canonical** asset source so a server
  restart syncs the updated file into `report_html/`.
- Use `python run_server.py` for the normal localhost experience path.

## 3A. Database schema changes require changelog + production migration discipline

Whenever you change any SQLite schema in this repo, treat the change as **incomplete**
until the audit trail, local schema snapshot, and production migration path are aligned.

Mandatory workflow:

1. **Record every structural change** in `db_schema_changelog.py` via
  `record_change(...)`. Capture, at minimum:
  - target DB file
  - operation (`ADD_COLUMN`, `DROP_COLUMN`, `RENAME_COLUMN`, `MODIFY_COLUMN`,
    `ADD_TABLE`, `DROP_TABLE`, `RENAME_TABLE`, index changes)
  - table and column name
  - reason for the change
  - files that read the column/table
  - referencing tables / foreign-key dependents
  - previous state and new state (name, type, nullability, default, notes)
2. **Maintain the separate local audit DB** `db_schema_changelog.db` as the detailed
  ledger of schema evolution for local development. This DB is the source of truth for
  what changed, why it changed, and what production migrations still need to absorb.
3. **Snapshot the local authoritative schema** after the change using
  `snapshot_current_schema(...)` so the target structure is preserved for future
  production migration work.
4. **Prepare the production migration path** using `db_migration.py`. The required flow
  for modified tables is:
  - rename the existing production table to `<table>_old`
  - create a new table with the exact updated local schema and the original table name
  - migrate compatible data from `<table>_old` into the new table
  - drop `<table>_old` only after a successful copy
5. **Human dependency:** the user downloads the production DB and places it locally.
  Once that DB exists, use `db_migration.py --plan-only` first, then execute the
  migration, and report diagnostics. If the production DB is not yet available, say so
  explicitly in the final response and mark production migration as pending.
6. **If the DB migration UI or diagnostics are touched,** update the coupled route, UI,
  server wiring, tests, and documentation together.

Preferred files for this workflow:

- `db_schema_changelog.py` — local audit log and schema snapshots
- `db_migration.py` — production migration planner and executor
- `DATABASE_SCHEMA_MIGRATION_PROTOCOL.md` — operator/developer runbook
- `.claude/skills/db-schema-migration-discipline/SKILL.md` — task workflow skill

## 4. Final-response contract (mandatory)

End every completed task with **two short sections, in this order**:

1. `How to experience latest changes on live localhost`
2. `How to test locally`

Before writing those sections, inspect project-native sources (`AGENTS.md`, `README.md`,
`package.json`, test files, helper scripts, existing CLI/docs) instead of guessing
commands, ports, or URLs.

The localhost section must include:

- The **exact commands you executed** during verification.
- The **exact additional commands** the user can run locally.
- The **exact server start command** (prefer `python run_server.py` from `E:\JIRA SCRIPT`
  unless a narrower repo-native command applies).
- The **exact localhost URL, route, or endpoint** to inspect (report the actual port if
  `run_server.py` selected a fallback).
- **Ordered manual steps** with expected visible behavior, focused on the latest change
  (not the whole app).
- A brief blocker note if startup or local experience was not executable in this
  environment.

Edge cases:

- If the change touches HTML, UI, templates, generated reports, or served assets, update
  coupled JS, CSS, generator, server, test, and relevant `.md` documentation files
  instead of changing HTML alone.
- If a command could not be executed, say so briefly and explain why.
- If no localhost run is applicable, state exactly:
  `How to experience latest changes on live localhost: Not applicable for this change`.
- If no local server run is applicable, state exactly:
  `How to test locally: Not applicable for this change`.

When verification is feasible in the current environment, execute the **narrowest
relevant local CLI commands yourself** before completing the task. Prefer focused checks
over broad expensive runs unless the change requires broader coverage.

## 5. Git / GitHub conventions

- When the user asks to **push to GitHub** (or equivalent) **without naming a branch**,
  use **`main`**: `git checkout main`, integrate any needed changes (merge/cherry-pick if
  they were done elsewhere), commit, then `git push origin main`. Only **`main`** /
  **`master`** trigger the Azure App Service deploy
  (`.github/workflows/azure-appservice-deploy.yml`).
- Do **not** default to `backup/*` or other side branches for routine pushes.
- Do **not** use backup branches or `backup/` snapshot folders for routine production
  deploys; keep backup artifacts gitignored (see root `.gitignore`).
- Production deploy packages **only what is committed and pushed** to GitHub (then
  rsync-staged without dev/test folders). Any file needed on the server must be tracked
  or produced in CI — local-only artifacts do **not** reach Azure.

### Git safety (Claude Code specific)

- Never update `git config`.
- Never run destructive irreversible commands (`push --force`, hard reset, etc.) unless
  the user explicitly asks for them.
- Never skip hooks (`--no-verify`, `--no-gpg-sign`) unless the user explicitly asks.
- Never force-push to `main`/`master`; warn the user if they request it.
- Avoid `git commit --amend` unless the user explicitly requested it **and** the HEAD
  commit is your own from this conversation **and** it has not been pushed.

## 6. Tooling conventions

- For file operations, use Claude Code's dedicated tools (`Read`, `Edit`, `Write`,
  `Glob`, `Grep`). Do **not** use `cat`, `head`, `tail`, `sed`, `awk`, or shell
  heredocs/echo redirection for file reading or editing.
- Reserve shell commands for actual system operations (git, python, npm, builds).
- Prefer `rg` (ripgrep) over `grep`/`find`.
- Long-running processes (dev servers, watchers) should be backgrounded; do not block on
  them.
- Do not add narrating comments to code. Comments should only explain non-obvious intent,
  trade-offs, or constraints. Never use comments to explain the diff you are making.
- Don't proactively create documentation files (`*.md`) or READMEs unless the user asks.
  Exception: this file (`CLAUDE.md`) and anything under `.claude/` are intentional.

## 10. Module documentation standard (mandatory — applies to every code task)

Every time you complete a code change — regardless of size — you **must** update the
`.md` documentation for the primary module changed **and** every linked, dependent, or
impacted module. This is non-negotiable and is part of the definition of "task complete".

When the change affects SQLite schema, the primary-doc update must also cover the schema
audit and production migration workflow in `DATABASE_SCHEMA_MIGRATION_PROTOCOL.md`, and
linked docs must mention any newly affected tables, columns, or migration dependencies.

### 10.1 Which docs to update

For every module touched by a code change, update (or create) its documentation file:

- **Root-level operational `.md` files** (e.g. `ASSIGNEE_HOURS_CAPACITY.md`,
  `IPP_PHASE_TRANSFORM_LOGIC.md`, `NESTED_VIEW_SCORECARD_FORMULAS.md`,
  `GENERATED_EXPORTS_COLUMNS.md`, `INCREMENTAL_SYNC.md`, `RLT_LEAVE_REPORT.md`,
  `DASHBOARD_REFRESH_CLI.md`, `AZURE_APP_SERVICE.md`, `EXPECTED_FILES.md`, `README.md`)
- **User-guide screen docs** under `docs/report-user-guide/screens/` and
  `docs/capacity-user-guide/screens/`
- **Module-overview docs** under `docs/report-user-guide/` and
  `docs/capacity-user-guide/`
- **Handover docs** under `handover/**/*.md`
- **Any other `.md` file** that describes behavior, fields, or data flow that the code
  change affects

When a changed module's doc file does not yet exist, create it in the nearest
established docs area (`docs/report-user-guide/screens/` for report modules,
`docs/capacity-user-guide/screens/` for capacity/settings modules, root-level for
operational scripts).

### 10.2 Mandatory content for every module `.md` file

Each module documentation file **must** contain all of the following sections.
Update only the sections affected by the current code change, but ensure every section
exists and is accurate after the task.

| Section | What to include |
|---|---|
| **Business Logic** | Rules, calculations, conditions, edge cases that drive the module's behavior. Enough detail that a developer can re-implement the logic from the doc alone. |
| **Business Cases** | Why the module exists. What real-world problem it solves. Who uses the output and when. |
| **Examples** | Concrete input → output examples for the key logic paths. Include realistic Jira data, dates, or numbers. |
| **Explanations** | Plain-English walkthrough of how the module works end-to-end. No code jargon — written for a business analyst. |
| **Front-end UI Fields** | Every visible field, filter, toggle, column, button, or label: its name, data type, default value, valid range, what it controls, and a worked example. |
| **Script Files** | List every `.py`, `.js`, `.html`, `.sql`, or config file that belongs to the module. Note each file's role (generator, server route, template, utility, test). |
| **Dependent & Impacted Files** | Files in *other* modules that read from, write to, or are affected by this module's output or DB tables. |
| **Table Schema** | For every SQLite table the module reads or writes: table name, column names, types, constraints, and a short description of each column's meaning. |
| **Data Flow** | A step-by-step description of how data enters the module (Jira API, Excel, DB), is transformed, and leaves (HTML report, API response, Excel export, DB write). Include which functions/routes handle each step. |

### 10.3 Linked and dependent module docs

After updating the primary module's doc, identify every module that:
- **reads** data produced by the changed module
- **writes** data consumed by the changed module
- **shares a DB table** with the changed module
- **imports** a function or constant from the changed module
- **renders UI** that displays the changed module's output

Update the **Dependent & Impacted Files** section of each linked module's doc to reflect
the current relationship. If a linked module has no doc file, create a stub with all
sections from 10.2 populated at a minimum level.

### 10.4 Enforcement rule

A task is **not complete** until:
1. The primary module's `.md` file is updated with all sections from 10.2.
2. Every linked/dependent module's doc has an accurate **Dependent & Impacted Files**
   and **Data Flow** section reflecting the change.
3. The final response lists every `.md` file that was updated.

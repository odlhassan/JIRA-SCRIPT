# RnD Muscle Utilization Settings

## Purpose

`RnD Muscle Utilization` is an admin planning page for managers who map RnD resources to Epics Planner work. The configuration route shows the epic catalog, the central planner, and the resource catalog. The view route shows only the central planner for review mode.

## Current Scope

The page loads live state through `/api/rnd-muscle-utilization`, supports skill/team/project configuration, and persists planner epics, resource mappings, and card order to SQLite tables in the dedicated RnD Muscle SQLite database. Planner moves and resource mappings update the browser immediately, then auto-save after 2.5 seconds without another planner action. Those tables are auto-initialised on first call.

## Business Logic

- **Skills** - The 11 default skills from `DEFAULT_RND_MUSCLE_SKILLS` are seeded once on first DB initialisation. Managers can add custom skills. Duplicate names are rejected case-insensitively.
- **Teams** - Managers create color-coded teams, assign skills and resources to them. Team skills describe the collective capability of the team, not mandatory skills for every team member. Team color must be selected from the fixed 10-color UI-friendly palette; duplicate team names are rejected.
- **Resources** - Resources are stored with display name, initials, email, optional team membership, and explicit resource skills. Canonical assignee/worklog names are synced into `rnd_muscle_resources` on page-state load. The right resource catalog hides resources marked resigned in the source capacity database, groups the remaining active resources by assigned team, and keeps resources without a team under **No team** at the end of the list. Team membership is resolved from `resource.team_id` first and falls back to `team.resource_ids`, so saved team assignments still render under their team even when the resource row does not carry a populated `team_id`. The catalog search filters active resources while the user types across name, initials, email, and team name. Resource catalog rows use a theme-aware tone derived from the assigned team's color, with the original color preserved as an accent; dark mode blends the color into the dark panel surface and uses a darkened strong tone for mapped-resource cards and Cluster name pills instead of filling them with the raw saturated team color. Resources without a team keep the neutral row treatment. Resource skill counts include only the skills selected directly for that resource.
- **Epics** - The epic catalog is sourced from `epics_management`. Epics whose matching `canonical_issues` Epic row in `canonical_refresh_state.last_success_run_id` has a `Completed` or `Resolved` status are excluded from the catalog, project counts, planner projections, backlog projection, and quick stats; punctuation variants such as `Resolved!` are normalized, while an active status in the current successful snapshot keeps a reopened epic visible. The status lookup is bounded by the latest `run_id` and the Epics Planner keys so it uses the canonical `(run_id, issue_key)` index instead of scanning historical canonical rows. Priority comes from the `priority` column. Budgeted hours are derived from `epics_management_plan_values.epic_plan` as `man_days * 8`.
- **Epic priority colors** - Epic rows and cards use a clean light-to-dark purple scale in the catalog, mapped-epic list, Cluster epic list, Product wise panels, and backlog. Light mode retains priority 3 light purple (`#EDE9FE`), priority 2 medium purple (`#7C3AED`), and priority 1 dark purple (`#4C1D95`). Dark mode replaces the light and highly saturated fills with progressively stronger dark plum surfaces: priority 3 `#2B2931`, priority 2 `#352640`, and priority 1 `#452064`, with separate muted text, pill, and border colors for contrast. The cards use flat fills with no gradient, glow, or left accent stripe.
- **Mapped epics** - The left planner area is the master collection list, similar to Firestore collections. It holds mapped/planned epic cards. Epics enter by dragging from the Epics catalog, clicking **Planner** in the catalog row, or clicking **Add to planner** from the backlog table. While a mapped epic card is being dragged for sorting, a dashed empty placeholder appears between cards or at the end of the list to show the exact drop position. The browser applies the new order instantly and queues the latest `sort_order` payload for `/api/rnd-muscle-utilization/planner/reorder` after the 2.5-second idle window.
- **Mapped resources** - The right planner area is the detail document list for the selected mapped epic, similar to Firestore documents. Dropping a resource from the right catalog onto this area maps it to the selected epic immediately in the UI. Resource cards are colored with their team's configured color and can be dragged to reorder per epic. Mapping, unmapping, and resource-card reorder actions replace the pending save payload for that epic and persist only after the user pauses for 2.5 seconds. When an active resource is already mapped to one or more planner epics, the right catalog row shows a **booked on n epics** chip; clicking it opens a high-layer menu listing the booked epic keys, names, projects, and allocation hours. The menu is positioned outside the clipped resource panel so it remains visible when it overlaps the planner.
- **Save progress** - A compact progress bar appears under the status line whenever planner changes are pending or actively saving. It advances while waiting for the idle window, continues while the database request is running, turns green on success, and turns red if auto-save fails. Text-only save feedback is not the only indicator.
- **Backlog** - The backlog table sits under the mapping section and is separate from mapped planner epics. Its Epic column displays the epic key and full epic name on separate lines, followed by priority, budget, dates, and **Remove** / **Add to planner** actions. Users can add to backlog by clicking **Backlog** in the left catalog, dragging an epic from the left catalog into the backlog table, or dragging an already mapped epic card into the backlog table.
- **Mappings** - Epic-to-resource assignments are upserted by `(epic_key, resource_id)` in `rnd_muscle_epic_resource_mappings`. The table stores `allocation_hours` and `sort_order`. Removing a resource card unmaps that resource from the selected epic.
- **Mapping workbook round trip** - The configuration toolbar provides **Export mappings** and **Import mappings**. Export waits for pending planner auto-saves and downloads `rnd-muscle-mappings-<UTC timestamp>.xlsx` with **Mappings**, **Resources**, and **Instructions** sheets. The Mappings sheet includes one row per resource mapping and a blank-Resource-ID row for each planner epic that currently has no mapped people, allowing the same downloaded workbook to be imported unchanged. Import validates the complete workbook before writing, then atomically replaces mappings only for epics represented on the Mappings sheet. Imported valid epics that are no longer on the planner are appended to it; planner epics absent from the workbook and all backlog data remain unchanged. An empty exported workbook is accepted as a no-op. The upload limit is 10 MB and only `.xlsx` files are accepted.
- **Planner views** - **Hierarchical** shows exactly two planner areas: compact stacked mapped-epic cards and mapped-resource cards for the selected epic. Mapped-epic sorting keeps the dashed insertion placeholder stable while the pointer passes over card gaps or the placeholder itself. The Cluster panel is hidden until the user explicitly chooses **Cluster**. **Cluster** shows mapped epics on the left and team-colored resource pills that display each person's full name. Its always-visible **Team colors** band identifies every rendered team color; hover details repeat the full resource name and team, and selecting an epic emphasizes its mapped people and connections. **Insights** renders a true area-proportional treemap: each tile's area is based on its value, so larger assignment counts or allocation units occupy larger rectangles. In Team mode, the **No team** tile is kept after named teams when values otherwise sort together. **Product wise** creates one horizontally arranged panel for each project chosen through **Configure Projects**, shows that project's mapped epics beneath its heading, and keeps a fixed **People involved** panel at the right. Project panels grow to share available width and move into horizontal overflow when their combined minimum widths no longer fit. Users can drag project panels to change their order; the order is stored in browser local storage under `rnd-muscle-product-panel-order-v1`. Its filters work in both directions and can be combined: clicking an epic narrows the people panel to active people mapped to that epic, while selecting one or more people shows the union of product epics involving any selected person. Clicking the selected epic again restores the broader people list without clearing the people selection. Selected person cards have a check indicator and stronger outline, the header reports both epic context and selection count, each card shows team and mapped-epic count, search matches person/email/team within the current epic context, and **Clear** removes only the people-to-epics filter. Project headers show the filtered count against the total and projects with no match remain visible with a helpful empty state. Epic priority colors, person team colors, and a team legend remain visible in this view.
- **View Mode route** - The **View Mode** button opens `/settings/rnd-muscle-utilization/view`. That page uses the same planner state and APIs but hides side epic/resource catalogs and configuration controls. It opens with **Product wise** selected by default, with the Product wise canvas visible immediately and no Hierarchical-view flash while state loads. Its primary planner canvas is exactly `100vh`; the page scrolls and places the backlog after that full-height canvas instead of squeezing both into the initial viewport. The configuration route continues to open on **Hierarchical**.
- **Theme controls** - The shared toolbar has a two-state **Dark / Light** toggle switch and **Color** picker. Choices are stored in browser local storage under `rnd-muscle-theme-mode-v1` and `rnd-muscle-theme-color-v1`, so the configuration and view routes use the same VS Code-style chrome, spacing, compact borders, accent color, themed scrollbars, and mode-specific epic/team color treatments.
- **Quick stats** - Computed on every page-state load: resources assigned to any epic, resources not yet assigned, total epics in the selected project scope, and high-priority epics with no resource assignment.
- **Project tabs** - The ALL tab appears first. The Configure Projects modal uses project checkboxes; the visible tab strip is limited to that selection.

## Mapping Workbook Columns

The exported workbook has five sheets: **Mappings** (required), **Resources** (reference only), **Skills**, **Teams**, and **Instructions**. Only Mappings, Skills, and Teams are read on import; Skills and Teams are optional so older exports without them still import cleanly.

### Mappings sheet

| Column | Import Role | Validation |
| --- | --- | --- |
| Epic Key | Required mapping identifier and import scope | Must exist in Epics Planner. Repeated rows group resources under the same epic. |
| Epic Name | Reference only | Exported for readability; import does not use it as an identifier. |
| Project Key | Reference only | Exported for readability. |
| Project Name | Reference only | Exported for readability. |
| Resource ID | Optional resource identifier | Must match `rnd_muscle_resources` when supplied. Leave blank on an epic row to clear or preserve an empty mapping set. Duplicate Epic Key/Resource ID pairs are rejected. |
| Resource Name | Reference only | Exported for readability; Resource ID remains authoritative. |
| Resource Email | Reference only | Exported for identifying similarly named people. |
| Team | Reference only | Uses direct `resource.team_id`, then the team's `resource_ids` fallback. |
| Allocation Hours | Optional mapping value; defaults to `0` | Must be numeric, finite, and non-negative when Resource ID is supplied. |
| Sort Order | Optional person order; blank uses worksheet order | Must be a non-negative whole number. Imported values determine ordering and are normalized to sequential database order. |

### Skills sheet (optional)

| Column | Import Role | Validation |
| --- | --- | --- |
| Skill Name | Creates a custom skill if no skill with that name (case-insensitive) already exists | Blank rows are skipped. Default skills (`DEFAULT_RND_MUSCLE_SKILLS`) are never exported here since they are seeded automatically on every database and don't need round-tripping. Matching existing skills are left untouched — this is additive, not a full replace. |

### Teams sheet (optional)

| Column | Import Role | Validation |
| --- | --- | --- |
| Team Name | Identifies the team; creates a new team if no team with that name (case-insensitive) exists, otherwise updates the existing team's color, skills, and members | Required per row. |
| Color Hex | Team color | Must be one of the 10 supported RnD team palette colors (same validation as Create Team). |
| Skill Names | Semicolon-separated list of skill names to assign to the team | Each name must match an existing skill — including one just created by the Skills sheet earlier in the same import — or the row fails with a row-specific error and the whole import is rejected (atomic, consistent with Mappings import). |
| Resource Names | Semicolon-separated list of resource display names to assign to the team | Each name must match an existing `rnd_muscle_resources.display_name` (case-insensitive) or the row fails the same way. |

Import order: Skills sheet rows are applied first (so newly-added skill names are available for the Teams sheet), then Teams sheet rows, then Mappings sheet rows. Teams/Skills import is additive/upsert by name — teams and skills not present in the sheet are left unchanged, mirroring how Mappings import only touches epics represented on that sheet.

## Table Schema

| Table | Key Columns | Purpose |
| --- | --- | --- |
| `rnd_muscle_skills` | skill_id PK, name, is_default | Default and manager-defined custom skills. |
| `rnd_muscle_teams` | team_id PK, name, color_hex | Manager-defined color-coded skillset teams. |
| `rnd_muscle_team_skills` | (team_id, skill_id) PK | Many-to-many team-to-skill associations. |
| `rnd_muscle_resources` | resource_id PK, display_name, initials, email, team_id | People available for epic assignment. |
| `rnd_muscle_resource_skills` | (resource_id, skill_id) PK | Many-to-many resource-to-skill associations. |
| `rnd_muscle_planner_epics` | epic_key PK, sort_order | Epics explicitly added to the planner epic area, ordered by saved card order. |
| `rnd_muscle_backlog` | epic_key PK, sort_order | Epics queued for later planning, rendered under the mapping section with Remove and Add to planner actions. |
| `rnd_muscle_epic_resource_mappings` | (epic_key, resource_id) PK, allocation_hours, sort_order | Resource-to-epic assignment with optional hour allocation and selected-epic resource card order. |

By default, `rnd_muscle_*` tables stay in the existing capacity DB (`assignee_hours_capacity.db`) so existing production team/resource configuration remains available. If `JIRA_RND_MUSCLE_UTILIZATION_DB_PATH` is explicitly configured, those tables are stored in that dedicated feature DB (`rnd_muscle_utilization.db` is the conventional filename) and auto-created by `_init_rnd_muscle_utilization_db`.

The feature reads Epics Planner and canonical Jira data from the source capacity DB (`assignee_hours_capacity.db` by default, or `JIRA_ASSIGNEE_HOURS_CAPACITY_DB_PATH` when configured). When a separate RnD DB is explicitly configured, `report_server.py` passes both paths to the service: the RnD DB for feature-owned writes and the capacity DB for read-only source lookups.

## Data Flow

1. **Page load** - `load_rnd_muscle_utilization_page_state(rnd_db_path, source_db_path)` initialises feature schema, syncs canonical resource names from the source DB, reads RnD tables plus source `epics_management`, `epics_management_plan_values`, `canonical_issues`, and `performance_resource_resignations`, removes Completed/Resolved canonical epics, and returns `RndMuscleUtilizationPageState`.
2. **Epic search** - `search_rnd_muscle_epics(rnd_db_path, text, project_keys, source_db_path)` filters the epic catalog by substring and project key.
3. **Team CRUD** - `save_rnd_muscle_team` validates that color is one of the 10 supported palette values and rejects duplicate names, upserts the team, replaces team skills, updates resource `team_id`, and returns fresh state.
4. **Skill CRUD** - `add_rnd_muscle_skill` rejects duplicates and inserts custom skills with `is_default=0`.
5. **Resource skill mapping** - `save_rnd_muscle_resource_skills` validates resource and skill IDs, replaces direct rows in `rnd_muscle_resource_skills`, and returns fresh state. The browser lets managers choose from the full skill list for each resource, independent of team skills.
6. **Backlog** - `add_epic_to_rnd_muscle_backlog` queues epics for future planning. `reorder_rnd_muscle_backlog` saves backlog order. `remove_epic_from_rnd_muscle_backlog` removes only the backlog row and does not alter active planner mappings.
7. **Planner epics** - `add_epic_to_rnd_muscle_planner` adds active mapped epics. The browser adds planner cards locally before the API call completes, then queues the POST for the idle-save cycle. `reorder_rnd_muscle_planner_epics` saves drag order. `remove_epic_from_rnd_muscle_planner` deletes the planner row and dependent resource mappings.
8. **Mapping** - `save_rnd_muscle_epic_resource_mapping` removes no-longer-assigned resources, upserts remaining assignments with allocation hours and sequential `sort_order`, and returns fresh state. Mapping, unmapping, and selected-epic resource ordering now share a debounced browser save queue keyed by epic, so rapid consecutive changes collapse into the latest payload before SQLite is updated.
9. **Mapped epic sorting** - Dragging a mapped epic shows a dashed insertion placeholder before or after the hovered mapped-epic card. Cards and placeholders use short transitions for a smoother drag feel. When the cursor crosses the placeholder or other non-card gaps inside the mapped-epics list, the browser keeps the existing placeholder target until the user reaches another epic card or the drop zone end. Dropping the card reorders local state immediately and queues `/api/rnd-muscle-utilization/planner/reorder`.
10. **Tab strip** - Server state exposes all project tabs; the browser stores selected tab projects in local storage and renders only the selected tabs.
11. **Theme preference** - The browser reads and writes `rnd-muscle-theme-mode-v1` and `rnd-muscle-theme-color-v1`, then updates CSS variables on load and whenever a user changes the toolbar controls. Scrollable page areas use the same CSS variables so vertical scrollbars change with the selected theme and accent color.
12. **Product panel order and bidirectional filters** - The browser derives Product wise panels from the project selection used by the project tabs, merges any saved project-key order from `rnd-muscle-product-panel-order-v1`, and appends newly selected projects after the remembered keys. Drag-and-drop writes only this browser preference; it does not reorder planner epics or change server data. The people panel excludes resigned resources and searches active people by name, email, or resolved team name. When `selectedProductEpicKey` is set, the people list is first limited to active resource IDs mapped to that epic and search applies within that subset. Selected resource IDs are held independently in the current browser session. With no selected people, all mapped epics render. With one or more selected people, `productEpicMatchesPeople` keeps an epic when any mapping contains both that epic key and a selected resource ID. The two filters therefore remain simultaneously active until the user toggles the epic or clears the people selection. These filters are client-side and do not change planner mappings or persisted data.
13. **Mapping workbook export** - `GET /api/rnd-muscle-utilization/mappings/export` loads unfiltered current state and builds the three-sheet workbook. Planner epic and mapping order are preserved. Reference columns show current names, projects, email addresses, and teams without becoming import identifiers.
14. **Mapping workbook import** - `POST /api/rnd-muscle-utilization/mappings/import` reads multipart field `workbook` (with `file` accepted as a fallback), validates extension, size, sheet name, headers, epic keys, resource IDs, duplicate pairs, allocation hours, and sort order, then calls `import_rnd_muscle_mapping_rows`. The service validates all identifiers again before opening one write transaction, appends missing valid planner epics, deletes existing mappings only for workbook epics, inserts the workbook mappings in normalized order, and rolls back the entire import if a write fails.

## Schema Change Notes

- Added `rnd_muscle_epic_resource_mappings.sort_order INTEGER NOT NULL DEFAULT 0` to preserve resource card order per selected epic.
- Added `rnd_muscle_planner_epics` to separate active mapped epics from the backlog plan-next queue.
- Moved all feature-owned `rnd_muscle_*` tables out of `assignee_hours_capacity.db` and into `rnd_muscle_utilization.db`. The capacity DB remains the read source for Epics Planner and canonical Jira data.
- `migrate_legacy_rnd_muscle_tables(legacy_db_path, rnd_db_path, drop_legacy=True)` copies existing local feature data into the new DB and removes legacy tables after row-count verification.
- The local changelog and schema snapshot were updated. Production migration is pending until a human-downloaded production DB file is provided locally.

## Related Import Change

Epics Planner Import expects and seeds the three support effort phases as planner columns: `ReadAPI Sup`, `SiteLayout Sup`, and `OmniAgent Sup`. These phases are treated like other most-likely input columns and can carry zero or positive man-days for every imported epic.
